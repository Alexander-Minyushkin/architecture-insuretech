# Архитектура с osago-aggregator

osago-aggregator необходимо иметь собственную базу данных, чтобы хранить информацию о заявках по которым нужно делать опрос и конфигурацию эндпоинтов.

core-app и osago-aggregator будут общаться через две очереди, одна на получение завок (osago-aggregator-input-queue), другая на публикацию предложений (osago-aggregator-output-queue)


osago-aggregator будет состоять из двух микросервисов, которые будут общаться через osago-aggregator-polling-queue

osago-aggregator-submitter 
- получает заявки из очереди osago-aggregator-input-queue
- создаёт заявку во внешней системе страховой компании
- создаёт команду в очереди osago-aggregator-polling-queue

osago-aggregator-receiver
- получает команду из очереди osago-aggregator-polling-queue
- пытается получить решение из внешних систем страховых компаний
  - Если решение получено, оно отправляется в очередь osago-aggregator-output-queue
  - Если не получено, но 60 секунд от создания заявки ещё не прошло, то команда повторно отправляется в osago-aggregator-polling-queue


Отдельная база данных для osago-aggregator не нужна, очередь osago-aggregator-polling-queue выполняет роль базы данных, чтобы не потерять заявки, по которым нужно получить ответ.

## Масштабирование
Наличие двух микросервисов позволяет масштабировать их независимо:
osago-aggregator-submitter  в зависимости от длинны очереди osago-aggregator-input-queue, либо от утилизации CPU/Memory.
osago-aggregator-receiver масштабируется в зависимости от длинны  osago-aggregator-polling-queue, либо от утилизации CPU/Memory.

## Паттерны отказоустойчивости
Использование очереди osago-aggregator-polling-queue позволяет естественным образом реализовать паттерны Retry и Timeout.
Например при ошибке от внешнего сервиса, мы отправим команду обратно в очередь, как буд-то просто не получили предложения.

Rate Limiter - на данный момент не понятно, есть ли в нём необходимость. 
Потенциально внешние системы могут иметь ограничения на использование API. В таком случае возникнет необходимост его реализации: дополнительная сложность будет связана с тем, что лимиты нужно будет согласовать между разными ЦОД.
В упрощённом варианте, каждый ЦОД может управлять своим лимитом который равен (External_API_Limit / Number_of_Data_Centers)
В данный момент Rate Limiter не поддерживается.


## Front-to-Back

Интеграция между веб-приложением и core-app потребует использования SSE, так как Бизнесу важно, чтобы на экране пользователя предложения от каждой страховой компании отображались сразу, как только от неё пришёл ответ.
