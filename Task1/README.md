# Планирование архитектуры

##  Стратегия масштабирования и отказоустойчивости
- Компания хочет сделать упор на развитие в регионах РФ.
  - Зачит нам потребуется деплоймент в нескольких **дата-центрах распределённых по территории** страны, нескольких зонах безопасности. Это поможет улучшить время отклика и масштабируемость.

- Планируется значительный рост количества пользователей и запросов. InureTech планирует в ближайшее время провести большую рекламную кампанию. Ожидается существенный прирост пользователей.
  - Это значит, что нагрузка на сервисы может меняться резко и непредсказуемо, например, если реклама случайно станет вирусной. С таким видом нагрузки лучше справляться с помощью **горизонтального масштабирования** 

- Для отказоустойчивости базы данных нужно использовать **кластер Patroni** в трёх разных дата-центрах.


## Конфигурацию развёртывания приложения в Kubernetes
Мы будем использовать независимые кластеры на каждом ЦОДе, это позволит обеспечить хорошую масштабируемость - в разных географических локациях может быть разная нагрузка. Они должны масштабироваться независимо.

## Балансировка нагрузки
Балансировка нагрузки будет производиться через GSLB. Это позволит направлять пользователя на ближайший ЦОД, для снижения времени отклика.

## Фейловер-стратегия

Для приложений и ЦОД-ов будет применяться Active-Active Стратегия.
Для базы данных за фэйловер отвечает Patroni: Active-Standby

## Шардирование
Сейчас объём данных 50 GB при резком росте возможно увеличение до 500GB с такими объёмами PostgresQL справляется без шардирования.
